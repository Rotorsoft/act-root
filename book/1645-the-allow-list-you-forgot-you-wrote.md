# The allow-list you forgot you wrote

A state in Act does not have to arrive in one piece. The framework encourages the opposite: keep state machines focused, split concerns into separate slices, and let several partials with the same name merge into one state at build time. A ticket's opening lives in one slice, its resolution in another, its archival policy in a third. This is the documented shape, and it is the shape the example applications use.

What nobody noticed is that only some of a partial's declarations survived that merge. If the third slice was the one that said `.autocloses({ keep: { days: 90 } })`, the retention policy was silently discarded and the events table grew forever. If it was the one that said `.discloses(...)`, every read of a sensitive field came back redacted, because the merged state had no predicate and the framework default-denies. If it was the one that passed `{ maxRetries: 2 }` to `.on(...)`, the retry budget fell to zero and the first concurrency conflict surfaced as an error to the caller. Move the identical declaration to the first-registered partial and all three worked. Nothing warned, nothing threw, and the behavior depended on registration order, which is the sort of thing a reader assumes cannot matter.

The mechanism is four lines that look like they copy everything. `merge_into_existing` in `libs/act/src/builders/merge.ts` builds the merged state by spreading the existing partial and then naming the fields it wants to combine: the schema, the initializer, the events, the actions, the patch handlers, the action handlers, the invariants, the snapshot strategy. Each of those gets real merge logic, some of it careful, and reading the function it is easy to come away thinking the spread carries the rest. It does not. The spread carries the rest *of the first partial*. Every field the explicit list fails to mention is a field where the incoming partial's value is thrown away, and the list had fallen behind the type. Six fields had accumulated on `State` since the list was written: the per-action options, the disclosure predicate, the autoclose predicate with its two day fields, and the archiver.

The obvious repair is to spread the incoming partial too and let the later value win. It does not survive contact with the function, because the careful merges are computed into the same literal. Adding `...state` after `...existing` either sits above the computed fields and changes nothing about the bug, or sits below them and clobbers a merged Zod schema with one partial's half of it. The spread that looks like the fix is the spread that breaks the thing the function was actually written to do.

Last-write-wins was the second candidate, and it has a real precedent: within a single builder chain, calling `.archives()` twice keeps the second archiver, and there is a test that pins it. But a builder chain is one author writing two lines in sequence, where the later line plainly means to replace the earlier one. Two partials in two different files are two authors who each believe they own the policy, and picking one by registration order is how this bug behaved in the first place. Choosing silently is the defect, not the cure.

What shipped instead was the rule the file was already applying one field over. `snap` had been handled correctly all along: whichever partial declares it wins, and two different declarations throw with the state's name in the message. Generalizing that into a small `pick_declared` helper and pointing the disclosure predicate, the archiver and the autoclose policy at it makes a conflicting pair of declarations a build error rather than a coin flip, and costs nothing when only one partial declares anything, which is the normal case. The per-action options are the exception that proves the rule: they are keyed by action name, so two partials declaring options for two different actions are not in conflict at all, and the right answer there is to combine the maps.

The autoclose policy needed one extra thought. Its two day fields are not independent settings a caller tunes; the builder derives them from the same policy object it turns into the predicate. Resolving each field on its own would let a predicate from one partial pair with a window from another and produce a retention rule nobody wrote. So the three move together, sourced from whichever partial owns the predicate, which is the smallest way to say that they are one declaration wearing three fields.

The reason this survived so long is worth more than the fix. The existing tests for partial states are thorough about the fields in the explicit list and silent about everything else, because a test written against a merge function naturally exercises the things that function visibly merges. The bug lived precisely in the gap between what the code appeared to handle and what it enumerated. A guard against the next one belongs in the same place: when a field lands on `State`, the question is not whether the builder sets it but whether the merge list names it.

The general shape is a spread followed by an explicit re-list, and it is worth recognizing on sight, because it wears the costume of a copy while behaving as an allow-list. The same pattern had already produced a sibling bug a wave earlier, where an option read inside a run-once block was baked for every later build from the same builder. Both are cases where the code says "and everything else comes along" and the reader believes it. When you find one, the useful question is not what the explicit list says. It is what the spread is quietly deciding on your behalf.
