# ACT-1356 — the snapshot that stood in for the head

A snapshot is supposed to be invisible. It is a performance artifact — a cached fold of everything up to a point, written so a cold load doesn't have to replay from zero. Nothing in the domain should ever key a decision on whether a snapshot happens to sit at the head of a stream, because whether one does is an accident of the snap cadence, not a fact about the aggregate. Autoclose forgot this, in two different places, and the two failures compounded into a stream that could never retire.

Autoclose is a synthesized reaction. On each triggering event it asks the store for the stream's head and count, and if the policy matches — `is` a terminal event, or the stream `reaches` N events, or a cooldown has elapsed — it throws a `CloseSignal` and the close-cycle guards and truncates the stream. To get the head it calls `query_stats`. And `query_stats`, asked plainly, returns the latest event of any kind, snapshot included.

The reaction knew this for the rolling-window case. A `keep` policy prunes the oldest domain events, and its decision keys on the age of the oldest *domain* event, so the reaction excluded snapshots — but only when `keep` was set. The terminate-only branch, the common `is`/`reaches`/`after` case, left snapshots in. That was fine until a terminal commit crossed a snap boundary. `snap()` writes its `__snapshot__` into the version slot right after the event that tripped the predicate, so the moment a `Resolved` also happened to be the second patch since the last snapshot, the head the reaction saw was the snapshot, not `Resolved`. An `is: "Resolved"` policy compared `head.name` against `"__snapshot__"`, found no match, and did not close. And because `is`-only has no later trigger — the stream is idle, resolved, waiting to be retired — nothing ever re-ran the reaction. The stream sat open forever. `reaches` had the milder version of the same disease: the snapshot inflated the count, so the threshold fired one real event early, and at a different real-event count depending on whether `keep` was also declared.

The fix for that half is one word: exclude snapshots unconditionally, the way the close-cycle's own head scan already did. Two functions computed "the domain head" and only one of them was right; making them agree is the whole change. But making the reaction fire correctly only exposed the second failure, one layer down, and this one was quieter because the stream now closed — it just closed into the wrong bucket.

The close-cycle guards a full close by committing a tombstone under optimistic concurrency: it reads the stream's head version, then commits the tombstone expecting that version, so a concurrent write between the read and the guard is caught and the stream is skipped rather than corrupted. The head scan excludes snapshots — correctly, because it also needs the domain head's id for the reaction-safety probe (a subscription advances its watermark on domain events, never on snapshots, so measuring lag against a snapshot's id would falsely mark every consumer as behind). But it used that same domain head's *version* for the tombstone's expected version. When a snapshot trailed, the true head was one version higher than the domain head, so the tombstone expected a stale version, the optimistic guard treated it as a concurrent write, and the stream landed in `skipped`. The reaction had done its job; the guard threw the result away.

---

**The wrong turn: one scan, one version, snapshots and all.**

The tempting simplification is to stop excluding snapshots in the head scan — take the true head for everything, version and id and name together, one query. It fixes the tombstone version instantly. It also breaks the safety probe and the restart seed. The safety probe compares each subscription's watermark against the head id; a subscription that has fully processed the domain stream sits at `Resolved`'s id, which is below the trailing snapshot's id, so a true-head id would report every caught-up consumer as lagging and skip the close as unsafe. The restart seed looks up which state owns `lastEventName` to rebuild from; `"__snapshot__"` is owned by no state. Both of those genuinely need the domain head. Only the tombstone's optimistic version needs the true head. The fields want different heads, so collapsing them to one is how you trade a visible bug for two subtle ones.

The actual fix keeps the domain-head scan exactly as it was and adds a second heads-only pass with snapshots included, used for one field: the guard version. It is a second round trip on the cheapest phase of a deliberately low-cadence operation, which is the right price to pay for not conflating two different questions. The domain head answers "what did a consumer last see, and who owns it." The true head answers "what version must my optimistic write expect." They were never the same question; the code had just been getting away with a single answer because no test committed a snapshot immediately before a close.

The rule worth keeping: a snapshot is a valid stream head for exactly one purpose — the optimistic-concurrency version, because that is the one place the *physical* head is what matters. Every domain decision — does the policy match, how many events are there, who owns the head, how far behind is a consumer — must look past it. When a single scan feeds both kinds of consumer, the domain ones set the terms and the physical version gets its own read.
