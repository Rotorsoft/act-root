# Transparent, except for the types

Encrypting a column is supposed to be invisible above the storage layer. You give the adapter a key, it writes ciphertext, and reads come back looking exactly as they did before. That is the entire promise, and the Postgres adapter states it plainly: the type-based discriminator that tells ciphertext from plaintext exists so mixed-data rollouts "read through transparently."

They did not read through transparently. A `Date` stored in a sensitive field came back a string as soon as encryption was on.

The mechanism is a seam between two layers that each behaved correctly. JSON has no date type, so every event store has to decide how a `Date` survives a round trip. Act's answer is a reviver: on the way out, an ISO-8601 string turns back into a `Date`. Postgres installs it as a pool-scoped JSONB type parser, so it fires as the driver materializes the column, and the SQLite adapter has its own equivalent for its TEXT columns. This was settled long ago and works.

Now encrypt the sensitive column. The value on disk is no longer a JSON object; it is a base64 string holding an authenticated envelope. The driver parses that column and hands back a string, and the reviver correctly does nothing, because there is nothing there yet — the payload is still sealed. The adapter then calls into the crypto package, which decrypts the bytes and parses the plaintext JSON itself. With no reviver. That parse is the last one that happens, it is the one that matters, and it is in the package that knows nothing about the convention.

So within a single row, a `Date` in `data` came back a `Date` and a `Date` in `pii` came back a string. The value was never lost; nothing was corrupted; the round trip was faithful in every respect except the one the application actually consumes, which is the runtime type. A reducer calling `.getTime()` throws. A comparison silently misbehaves. And the change that caused it is a configuration flag flipped by an operator, possibly months earlier, in a completely different file from the code that breaks.

There was a second half, which is what made the shape obvious. SQLite had the same bug on the *plaintext* path: its sensitive-column read parsed with a bare `JSON.parse` while `data` and `meta` went through the reviving helper two lines away. That one had been filed on its own. Seen together, the two are one fact stated twice: **the sensitive column took a different parse path from every other column, and each place that path was rebuilt, the reviver was left behind.**

That reframing decided the fix. The tempting option is to teach the crypto package about ISO-8601 dates: no new public surface, one line, done. It is the wrong one. That package deliberately makes no policy about payload semantics — it moves bytes and it authenticates them — and non-Act consumers storing a string that happens to look like a timestamp would suddenly get a `Date`. Worse for this particular bug, it would create a *second* reviver implementation, living in a third package, that must stay in step with the two that already exist. The defect is divergent parse paths. Curing it by adding a parse path is not a cure.

So `decrypt` takes an optional reviver and the adapters pass the one they already use for their own plaintext columns. The sensitive column stops having its own opinion about JSON and inherits the adapter's. That is a smaller idea than it sounds: the crypto package still makes no policy, it just stops silently discarding the caller's.

The regression lives in the store TCK rather than in either adapter's tests, and that placement is the part worth keeping. There are four cells here — two adapters times encrypted and plaintext — and three of them were broken while one was fine. Any test written where the bug was found would have covered one cell and left the neighbours to be discovered later, separately, by someone else. The contract is "a `Date` is a `Date`, in every column, on every adapter, whatever the operator configured," and a contract that holds across a matrix belongs in the file every adapter is compelled to run.
