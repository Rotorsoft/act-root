# The cache that outlived its Act

The bug was one word in a documentation sentence, and the sentence was ours.

The architecture guide describes what a builder shares when it produces more than one Act, which is the shape multi-tenant deployments use: hold the blueprint in a constant, call build once per tenant, hand each Act its own store and its own cache. The guide lists what gets shared by reference, and the list reads registry, states map, batch handlers, deprecation set, followed by the reassurance that the whole lot is read-only after the first build. Every item on that list is a lookup table. Every item except one.

State projections compile into a batch handler. That was the good insight from ticket 1125, and it still is: the drain pipeline already knew how to hand a window of events to a single function and only advance the watermark once the function returned, so the fold engine needed no orchestrator changes at all. The builder emits a closure and the existing machinery carries it. But the closure is not a lookup table. It owns a map of folded state, one entry per stream, and that map is the entire point of the feature, because holding the fold in memory is what turns ten million row writes into fifty thousand. The performance property and the sharing bug are the same object.

So two Acts built from one builder shared a cache keyed on stream name alone, with no notion of which store the stream lived in. Tenant A folds `c-1` and puts it in the map. Tenant B, with its own Postgres schema, its own connection, its own cache, drains its own `c-1`, and gets a warm hit on tenant A's entry. B's first-sight load against B's store never happens, because the cache said there was nothing to look up.

That much is a disclosure bug, and bad enough. The second half is worse and took a moment to see. The engine guards against re-applying events it has already folded by comparing the incoming event id against the frontier stored in the cache entry, and event ids are per-store. Tenant B's first event legitimately carries id zero in tenant B's store. Tenant A's frontier, sitting in the shared entry, is also zero. Zero is not greater than zero, so B's event is not folded. Not delayed, not folded late, not eventually reconciled on the next pass: dropped, permanently, while the row is marked dirty and flushed with A's numbers in it. The event store stays perfectly correct throughout. Only the read model lies, which is the half of the system anyone actually reads.

The reason no test caught this is worth sitting with, because it is the same reason the sentence in the guide went unchallenged. Every fold test in the suite mints a fresh builder and a fresh projection, because that is the natural way to write an isolated test. Isolation was assumed at the wrong layer, so the suite never expressed the one composition that breaks. And the composition is not exotic. It is the pattern the guide recommends for multi-tenant SaaS, and it is also `fixture`, the helper the project's own instructions name as the default way to write tests, which builds a scoped Act per test off a builder held in a module constant. Any test file with two state-projection tests in it was already getting a wrong row in the second one, silently, and would have kept getting it.

The fix is small once the shape is clear, and the discipline is in what it does *not* move. The validation stays where it was: resolving which merged state a projection folds, and refusing a projection whose register does not cover the state's whole register, are genuinely one-time jobs and belong in the first build. What moves is the handler construction. The builder records the validated ingredients and mints the handler per build, so each Act gets its own map. The cache still spans drain cycles within an Act, which is where the write amplification win comes from, so nothing about the performance argument changes. Building per Act also fixed a quieter thing nobody had noticed: `validateFoldedState` is a per-build option that feeds the fold's patch function, and a shared handler froze the first build's choice for every tenant after it.

There is a general lesson filed under a specific name. A blueprint shared by reference is safe exactly as long as everything on it is inert, and the moment one entry acquires mutable state the sharing becomes a leak with no error, no log, and no lifecycle event to notice it by. The list in the guide made that check easy to skip, because a list invites you to check that a new item belongs on it rather than to ask whether the list's promise still holds. It now says stateless batch handlers, which is a longer sentence and a true one.
