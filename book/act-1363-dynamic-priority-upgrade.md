# ACT-1363 — the priority that only the first event got to set

Priority in Act is a scheduling hint with a simple promise: when several reactions want the same target stream at different priorities, the highest one wins. The store enforces it literally — `subscribe` upserts priority through `GREATEST(stored, new)`, so no matter what order the registrations arrive in, the target ends up at the maximum anyone asked for. The documentation states this as a runtime invariant, not just a build-time one, and for static reactions it is exactly true: every static target is subscribed once at startup with its build-time-merged priority, and that is the end of it.

Dynamic resolvers are where "runtime" starts to mean something. A resolver is a function of the event: `.to((e) => ({ target: \`leaderboard-${e.data.region}\`, priority: e.data.tier === "premium" ? 5 : 0 }))`. The same target — one region's leaderboard — can be resolved at priority 0 by a free-tier event and at priority 5 by a premium one. Which event arrives first is an accident of traffic. The invariant says it shouldn't matter: the target should settle at 5 regardless of order.

It didn't. The correlate cycle discovers dynamic targets by scanning committed events past a checkpoint, resolving each reaction, and subscribing whatever new targets it finds. To avoid re-subscribing the same target on every scan, it kept a set of targets it had already seen and skipped anything in it: `if (resolved && !this._subscribed.has(resolved.target))`. The first time `leaderboard-us` was resolved — say by a free-tier event at priority 0 — it was subscribed at 0 and added to the set. Every later scan that resolved `leaderboard-us` again, at any priority, found it already in the set and skipped it before `subscribe` was ever called. The store's `GREATEST` is a real guarantee, but it only fires when `subscribe` runs, and for an already-seen dynamic target `subscribe` never ran a second time. The premium event's priority 5 was computed, discarded, and forgotten. The leaderboard sat at 0 forever, starved in the lagging frontier under exactly the saturation conditions priority exists to handle — with no error, no warning, nothing.

There was already a fix in this neighborhood that looked like it should have covered this. ACT-1255 made the *within-scan* merge carry the winning reaction's lane, not just its priority, when two reactions in the same scan window resolve the same target. But that merge only reconciles reactions inside one scan. The free event and the premium event land in different scans — different `correlate()` calls, seconds or minutes apart. Nothing reconciled a target's priority *across* scans, because the dedup set short-circuited the target out of consideration before any cross-scan merge could happen.

---

**The wrong turn: re-subscribe every dynamic target on every scan.**

The blunt fix is to drop the dedup entirely and let `subscribe` run for every resolved target every scan. `subscribe` is an idempotent UPSERT and `GREATEST` would then always see the higher priority, so correctness is restored. It also reintroduces the exact cost the dedup existed to avoid. An app with millions of dynamic targets — one leaderboard per region, one workflow per order — would re-issue a subscribe for every target on every scan of the back-scan window, turning a bounded restart cost into a per-scan flood of redundant UPSERTs. The dedup is load-bearing for memory and I/O; removing it trades a rare priority bug for a permanent throughput regression.

The fix keeps the dedup but makes it remember *what* it deduped, not just *that* it did. The `_subscribed` set becomes a map from target to the priority it was last subscribed at. A target is let through the guard when it is new, or when a later scan resolves a strictly higher priority than the recorded one — precisely the cases where `subscribe`'s `GREATEST` has something to raise. A lower-or-equal resolution still short-circuits, so the steady-state flood never happens; only a genuine upgrade pays for a re-subscribe, and an upgrade is rare by construction. Static targets are recorded at positive infinity, so a dynamic resolution can never re-open one — their priority stays owned by the build-time path, exactly as before. The map is still an LRU with the same bound, so the memory story is unchanged.

The rule worth keeping: a dedup that guards a monotonic upgrade has to store the value it is deduping against, not a presence bit. A presence set answers "have I seen this?" — but the question priority actually asks is "have I seen this *at least this high?*", and only a map can answer that. The set was the right shape for a target that gets subscribed once; it was the wrong shape the moment a target's priority could climb.
