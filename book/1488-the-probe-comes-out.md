# Taking out the question

For most of the framework's life, a worker looking for work asked the event log a question, once per subscription, every time it looked. Does this stream have anything past its watermark? And this one? And this one? The question was cheap on its own and ruinous in aggregate, because the number of times it got asked was the number of subscriptions, and under the reaction shape everybody writes, one target per aggregate, the number of subscriptions is the size of the domain. A system with a million aggregates paid for a million questions every time any worker went looking, whether or not a single event was waiting. Idleness cost the same as saturation. That is not a slow query, it is a cost attached to the wrong noun.

The work mark replaced the question with an answer written down in advance. Correlate walks events forward, resolves each to the targets that care, and records on the subscription row the highest event id that resolved there. A stream has work exactly while its watermark sits below that mark, which is a comparison between two columns of one row. The column arrived first, then the producer, and each shipped behind the old probe so nothing changed while the pieces were proven. This is the change that takes the probe out, and the shape of the diff says something about how long a defensive fallback should live: the code deleted was three SQL arms on Postgres, a JavaScript loop on SQLite, and about a hundred tests that had been quietly encoding the pull model as though it were physics.

The SQLite loop deserves its epitaph. It selected every eligible subscription with no limit, then ran one existence query per candidate, in JavaScript, with no early exit once the lease budget was full, and it did all of that inside the writer transaction. So a claim was linear in subscriptions, and every commit in the process queued behind it. The Postgres fix that had made the same probe sargable could not port, because there was no SQL for a planner to optimise, only a for loop. Deleting it is the single largest improvement in that adapter's history, and it came from deleting rather than adding.

The tests are where the change stopped being mechanical. About a hundred failed at once, and they split into two piles. Most needed one line: they committed an event and expected to claim it, which in a real application means correlate ran in between, and in a store test means nobody did. Those got a helper that does correlate's job honestly, marking each subscription to the newest event inside its own source window, and the fix reads as documentation of the new contract rather than as an accommodation of it.

The second pile was the interesting one. There was a block of contract tests asserting that claim matched a subscription's source exactly, never overmatching a sibling stream sharing a prefix, and another asserting that a pattern source claimed only when a matching stream really had work. Both came from real bugs with real tickets behind them. Both were now testing a behavior the store no longer has, because a claim that never reads the event log cannot match anything against it. The matching did not disappear, it moved up a layer: correlate applies the source window when it decides which events may raise a mark. So the tests moved with it, and the comment left behind says where they went. Deleting a test that encodes a hard-won lesson feels wrong until you notice the lesson is still enforced, one level up, where the knowledge now lives.

Two bugs fell out of the exercise, and both were found by tests whose premises had quietly gone stale rather than by reasoning. A lane worker stopped closing a stream because correlate raising a mark on a target that was already subscribed did not arm the drain; arming keyed off newly registered rows, which was a fine proxy while the probe could find work on its own and is no proxy at all once eligibility comes from the mark. And the close cycle's safety check kept a conservative arm treating an unmarked row as a reader still in flight, which stopped making sense the moment an unmarked row became something claim would never serve either. Neither was visible in the diff. Both were visible in a test that had been written to assert something else.

The upgrade path is the part I would defend hardest, because the obvious version is wrong twice over. Existing installs have rows with no mark, correlate cannot help them because its cursor is long past their events, and a claim that trusts marks alone would leave those reactions silently dead. The first instinct is to compute the truth: for each unmarked row, ask the log what the probe would have answered, and write it down. That works and it is slow, and it puts the old N+1 back into startup as a farewell gesture. The second instinct is a constant, and the constant that suggests itself, the newest event in the log, is exactly the backfill an earlier design note rejected for making every stream look pending at once.

The reframing that fixes it is to stop treating a mark as a promise about the log and let it be, once, an invitation. The value written says worth one look, not there is work here. Every pre-existing subscription gets claimed a single time, fetches its window, handles whatever is really in it, acks, and settles at an honest position, after which the mark means what it always means. One extra cycle per subscription, paid once, in exchange for a migration that is a single statement with no probing. The precision the guess gives up is restored by the machinery that was going to run anyway.

That trade has a boundary worth marking, because it is tempting to reach for it again. It works for a one-time transition, where the wasted cycle is amortised over the life of the install. It fails as a steady-state strategy: coarsening every scan's mark to the window's newest id would collapse the write into one cheap statement, and would also make every target the window touched look pending on every scan, because under the per-aggregate shape a target's own source rarely holds the newest event. What is one wasted cycle at migration becomes a permanent tax per target per scan. The same idea, evaluated against a different denominator, changes sign.

What is left is the number the whole plan was for. Claim time no longer grows with the number of subscribed streams: on Postgres it is under two and a half milliseconds at a hundred thousand subscriptions, where the probe took a hundred and eighty. What the cost tracks now is how many streams actually have work, which is the backlog, which is the thing an operator can reason about and act on. The axis moved from how much history you have accumulated to how far behind you are, and those are different questions with different answers.
