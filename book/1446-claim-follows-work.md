# Three adapters, three answers, no question

A stream that has just been subscribed sits at watermark minus one, meaning nothing has been processed yet. Ask the three store adapters whether such a stream should be handed to a worker when there are no matching events anywhere, and you got two answers. The in-memory store short-circuited: if the watermark is below zero, claimable, full stop, no probe of the log at all. Postgres did the same thing in SQL, with a dedicated arm of its eligibility union that selected every subscription at a negative watermark without looking at the events table. SQLite had no such branch and simply asked its one question, are there events past this watermark, which for an empty log answers no. So the same call sequence produced one lease on two adapters and zero on the third.

The ticket filed this honestly as a divergence rather than a defect, because no harm could be demonstrated. When there are no matching events there is genuinely no work, so the adapters that claim are handing out an empty lease that acks a no-op, and the subscription rows already exist either way. Nothing observable diverges downstream. What made it worth filing was narrower and better: three implementations disagreed on an observable outcome of a contract method, and the contract test suite said nothing about it, which meant any third-party adapter was free to pick either answer and be equally right.

Deciding required knowing whether that single visit was load-bearing. It was not, but working that out turned up something else. Following the empty lease through a drain cycle, the watermark it acks to is not the fresh minus one but zero, because the cycle computes its fetch window by reducing over the fetched entries with a seed of zero and an empty fetch has no last event to offer. Harmless on Postgres and SQLite, whose event ids begin at one, so acking to zero still leaves the first real event ahead of the watermark. Not harmless on the in-memory store, whose ids begin at zero. A probe made it concrete: subscribe a fresh stream, claim it while the log is empty, commit the first event during the cycle, ack the empty result, and the event is gone. Watermark at zero, event id zero, never delivered, never claimable again.

That reframed the choice. One option was to teach SQLite the short-circuit so all three agreed on claiming. It would have made the adapters consistent by propagating a window that only one-based ids were papering over, and it would have kept an empty lease and a no-op ack for every subscription that had not seen work yet. The other option was to delete the special case from the two adapters that had it, so a claim follows work rather than registration. That removes the window instead of spreading it, saves a lease and a cycle per subscription, and turns out to need no compensating logic at all, because every comparison already in place answers correctly at minus one. An event id greater than minus one is any event id. The special case had been doing nothing that the general rule did not already do, except in the one situation where doing nothing was the correct answer.

The reason the second option is also the right long-term shape is that the framework is moving toward a claim that does not consult the event log at all, where a stream is claimable exactly when the subscription side holds a mark saying so. Under that design a fresh subscription with no events has no mark and is therefore not claimable, which is the behavior this change adopts. Choosing the other option would have meant inventing a special case now and then reproducing it later inside a design whose whole point is to have fewer of them.

Two tests now pin the contract for every adapter, present and future. One asserts that a fresh subscription with no matching events is not claimed. The other asserts that the same subscription is claimed the instant its first event lands, and that the lease still opens at minus one, which is the property that keeps a zero-based first event inside the fetch window rather than behind it. A third test lives with the in-memory adapter, because only that store issues an id of zero, and it names the loss directly rather than the mechanism that caused it.

One existing test had to change, and it is the most interesting artifact of the whole exercise. A case checking that a pattern source is not claimed when nothing it matches has work used a second subscription as a control, to guarantee the second claim was non-empty. Its comment said, in effect, both are fresh subscriptions so both appear in the first claim. That test was silently depending on the behavior being removed, which is what a test does when the thing it depends on was never stated as a rule. Now the control's absence from the first claim is asserted rather than assumed, and the rule it depends on is written down in the suite two describes above.
