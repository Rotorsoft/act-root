# The bound goes before the effect

Act ships three stores that implement one contract, and a compatibility kit that proves they agree. The kit is thorough about what the framework does. It turned out to be silent about what happens at the edges of the arguments it passes, because the framework never passes those edges, and a test suite written from the caller's habits inherits the caller's blind spots.

Three divergences lived in that gap, all in the in-memory store, all the same mistake: a bound applied after the thing it was supposed to bound.

The first one is worth the whole ticket on its own. Leasing a stream takes a duration, and the in-memory store recorded the lease holder only when that duration was positive. Both SQL adapters record the holder unconditionally and let the duration decide the expiry, which is the only reading that makes sense once you notice that acknowledging work is gated on being the holder. Grant a lease with no holder recorded and the lease itself still comes back to the caller, which processes the events and acknowledges them, and the acknowledgement is dropped because nobody holds the stream. The watermark never moves. The next drain redelivers the same events, forever, without a single error anywhere.

What makes it more than a curiosity is that the duration is legal configuration. The schema accepts zero, and the code that threads it through uses the nullish operator, which passes zero along rather than falling back to the default. So an operator can write a fully type-checked application that redelivers every event on every drain, in silence. The in-memory store is documented as being for development and testing, which is the whole reason the failure is worth fixing rather than filing: development and testing is where a person meets it, without the production adapter's behavior to compare against.

The other two are smaller and identical to each other. Both enumerating reads counted a row, then checked whether the count had reached the limit. Ask for zero rows and you get one, because the check that would have stopped it runs after the row has already been handed to the caller. Both SQL adapters express the bound in the query and return nothing. Nobody in the framework asks for zero rows, so nobody noticed.

There is a symmetry in the three that is worth keeping. In each, the guard was placed where it reads naturally in prose rather than where the effect happens. "Lease it, if the duration is real" reads fine and quietly makes the duration decide whether the lease exists. "Emit the row, then stop if we have enough" reads fine and quietly emits one too many. Writing the bound before the effect it bounds is not more correct in some abstract way; it is just the only placement where the degenerate input does the degenerate thing.

The repair to the suite matters more than the repair to the store. A conformance kit that only feeds the values a caller happens to use is testing the caller, not the contract. The three cases added here pass a zero where the suite always passed a positive number, and each one carries a control that does the ordinary thing with the same code path, so a future reader can see that the boundary is the only variable. All three were red against the unmodified in-memory store and green against Postgres and SQLite unchanged, which is exactly the shape a divergence report should have: the outlier is named by the test, not by the author.

The same sweep that found these went looking for more of the family and came back mostly empty. A full differential of what the mutating methods return and what a subscription row looks like afterwards found the three adapters in agreement, as did a wide matrix of query and statistics options. One further edge, a negative limit, is a genuine three-way disagreement and is being left alone deliberately: it belongs to the family of nonsense inputs already recorded elsewhere, and inventing a contract for it would be specifying behavior for a call nobody should make. There is a difference between a boundary value a real configuration can produce and an input that is simply wrong, and only the first one earns a rule.
