# The default nobody tested

The SQLite adapter shipped with a default that read like a courtesy. Construct a store with no arguments and you got `file::memory:`, an in-memory database, which is exactly what a getting-started snippet or a dev server wants. What actually happened was that libSQL handed every connection its own private database and made no promise about which connection ran your next statement, so the schema created by `seed()` lived somewhere the following `commit` could not see. The commit still returned. It reported one committed event, version zero, no error. The readback then threw `no such table: events`. A second commit failed outright and versioning restarted from zero, which is the tell that the first write never landed anywhere durable. Of all the ways a store can be wrong, this is the worst one available: it told the caller yes and then lost the data, and it did so on the code path a person reaches for first, before they know enough to distrust it.

The suite was green over this for as long as the adapter existed. Every spec in the package constructed the store with an explicit `file:` URL, because tests want a database they can inspect and delete, and the TCK asked adapters for a factory rather than for their defaults. The configuration under test was never the configuration a newcomer gets. That is the part of the bug worth remembering, more than the libSQL detail: a default is a code path like any other, and an untested one drifts from its documentation quietly. The doc-comment on `SqliteConfig.url` had already drifted, promising a default of `:memory:` while the code used `file::memory:`, two spellings of the same failure.

The obvious repair was to make in-memory work, since a default that functions is friendlier than a default that refuses. libSQL turns out to serve exactly one in-memory mode that survives a round-trip, the shared cache form, and it refuses the query parameter that would let each store name its own private database. So the friendly fix bought a working default by making every default-constructed store in a process share a single database, one that outlives `dispose()` and is visible to any other store that asks for memory. That trades silent data loss for silent cross-talk, which is a smaller crime committed in the same category, and it sits badly next to a framework that already ships `InMemoryStore` for tests and single-process development. A SQLite adapter has no business defaulting to memory when the memory adapter is one import away. So the default went away entirely. Constructing a store without a URL now throws at construction, with a message that names the three things a caller might have meant, and the constructor signature narrows so the mistake is usually caught by the compiler before anyone runs it.

Refusing the default did not settle what to do for the person who asks for memory on purpose. Leaving `:memory:` broken would have been consistent and useless, since the caller spelled out their intent and the adapter can honor it. Every in-memory spelling is now normalized to the shared-cache form, which works, and the caveat about the database being process-wide is written down where the option is documented rather than discovered. The one case that still refuses is a URL that explicitly asks for a private cache, because that is the original failure requested by name, and rewriting an explicit parameter into its opposite would be a worse habit than throwing.

The other half of the ticket mattered more than the fix. A TCK that never constructs an adapter the way its README does will let the next adapter ship the same bug with a conformance badge, so the store TCK gained an optional `default_factory`. Supplying it opts into a single case that admits two outcomes and outlaws the third. Construction may throw, which is an adapter saying honestly that it has no safe default, and an operator sees that immediately. Or construction may succeed, in which case the store has to seed, accept a commit, accept a second commit that advances the version, and return both events on readback. What it may not do is accept a write and lose it. Writing the assertion as a disjunction felt weak for about a minute, until it became clear that the disjunction is the contract: the suite does not care which answer an adapter gives, only that it does not give the third one. In the repository the two branches are both live, since `InMemoryStore` takes the round-trip path and `SqliteStore` takes the refusal path, and pointing the SQLite factory back at the old URL with the normalization removed reproduces the ticket's error inside the new case, which is the only evidence that a regression test is worth its line count.

Postgres was left out of it on purpose. Its defaults point at a local database on the standard port, and the docker instance the tests use listens elsewhere, so a case wired to those defaults would pass or fail based on what happens to be running on the developer's machine. A test whose verdict depends on the room it runs in is worse than no test, because it teaches people to ignore a red result.

The principle underneath is one that keeps recurring in this codebase. Anything a system offers as a convenience is a promise, and a promise nobody exercises decays into a lie at the speed of its dependencies. The versioning convention on deprecated events works the same way, refusing at build time rather than warning at runtime, and the seed-sync contract earns its keep for the same reason, by having a test that hand-builds the oldest supported schema instead of trusting that upgrades still work. When a default cannot be honored, the honest move is to delete it and say why in the error message, which costs a caller one line and saves them a debugging session that starts from the false premise that their data was written.
