# What graceful means when the work is a reaction

The framework had a section in its production checklist called graceful shutdown, and it was honest about the part it covered. Signals are handled, disposers run in reverse registration order, the HTTP server stops accepting connections before the store closes so an in-flight request can still finish its commit. All true, and all about requests. The word reaction did not appear anywhere in it, which turned out to be the interesting omission, because a reaction is the one kind of work in an event-sourced system that a shutdown can quietly throw away.

Here is what actually happened on a rolling deploy. A reaction handler is parked on an await, calling a payment provider or writing to a reporting database. SIGTERM arrives. `shutdown()` stops the correlation worker, cancels the settle cycle, stops the breaker, and calls stop on every drain controller, which clears their timers. Then it returns, measured at zero milliseconds, with the handler still parked. The handler keeps running, because nothing cancelled it and nothing was awaiting it. When it finally completes, it submits an ack that lands after teardown, and a dropped ack is a short return, so the round of work is discarded and will be redelivered. Nobody sees any of this, because the listeners were removed on the first line of shutdown. Meanwhile the stream it was working sits leased, and the replacement worker that just came up cannot claim it until the lease expires, which for a slow lane is the thirty seconds the checklist itself recommends configuring.

So three costs, and the middle one is the one operators feel: dead time on every deploy, proportional to a value they chose for an unrelated reason.

The naive repair is to await the in-flight work, and it is genuinely worse than the bug. A handler stuck on a hung socket would hold the deploy open forever. Trading bounded dead time for an unbounded hang is not a fix, it is a different incident. So the shape has to be a budget: wait, but only so long, and proceed regardless when the budget is spent. That much is the same reasoning every HTTP server with a drain timeout arrived at.

The question that took the most thought was what the budget should default to, because the answer determines whether the fix helps anyone who does not read release notes. A fixed five seconds is easy to document and matches what web servers usually pick, and it is wrong here for a specific reason. An operator who configured a lane with a thirty second lease was making a statement: handlers on this lane legitimately take that long. Cutting them off at five seconds reintroduces the bug precisely for the lane that cares most about it. Which points at the answer sitting in the configuration already. The lease is the system's existing expression of how long a handler may hold a stream, so it is the honest ceiling for how long teardown should wait for one. A lane that pinned no lease contributes the same ten second fallback drain itself uses, and the whole thing is capped at thirty seconds, because past that point a single parked handler is no longer expressing the operator's intent, it is holding a deploy hostage.

There was a subtlety in that derivation that a test caught rather than the design. The first implementation took the maximum lease across all the lanes, which sounds right until you notice that an app with a three second slow lane and an idle default lane waited ten seconds, because the idle lane contributed the fallback. Waiting on behalf of a lane with nothing running is indefensible, so the budget now comes only from the lanes that actually have a cycle in flight. The lesson is not about lanes. It is that a default derived from configuration has to be derived from the configuration that is relevant right now, not from everything the operator once declared.

Two smaller decisions came along with it. The order of teardown changed so that listeners are removed after the wait rather than before, which means an acked subscriber finally observes the work that completes during the grace window. That was free, and it closes the third cost from the original report. And the ticket's other suggestion, releasing the claimed leases on the way out instead of waiting for the handler, was deliberately left on the table. It is a good idea and it composes with this one, but releasing a lease has no store method, so it would mean new port surface, new contract tests, and three adapter implementations, to buy something the bounded wait already provides whenever the handler finishes in time. It is the right follow-up if the exhausted-budget path turns out to be common, and building it before that evidence exists would be guessing.

What generalizes is the framing. When a system has to stop, the interesting question is never whether to wait, it is what number to wait for, and the best answer is usually already written down somewhere in the configuration as an expression of the same underlying intent. Reaching for a fresh constant is how a system accumulates knobs that disagree with each other. The lease and the shutdown budget are answering the same question, one at the start of the work and one at the end, and they should not be allowed to give different answers.
