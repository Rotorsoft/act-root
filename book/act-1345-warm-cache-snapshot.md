# ACT-1345 — the snapshot a warm read refused to see

The cache is a checkpoint. An entry says "stream X was in state S as of event id N," and a warm load trusts it: instead of folding the stream from the beginning, it asks the store for everything after N and replays only that tail onto S. The optimization is the whole reason repeated reads on a hot stream stay cheap. The query it issues is `{ after: cached.event_id }`, and for years that was the entire story.

The store has a second query flag that never came up in the same breath. `with_snaps` tells it to include `__snapshot__` rows in the result; without it, snapshots are filtered out, because a normal fold walks domain events and a snapshot is a synthetic rebaseline it usually doesn't want mixed in. The warm read didn't set the flag. It didn't need to — the events after a fresh checkpoint are just the handful of domain events committed since, and there is no snapshot among them to care about. The two flags lived in different mental compartments and nothing ever put them in the same query.

Windowed close is what puts them there. A `keep` prune deletes the prefix of a stream below its closest safe snapshot — the old events are gone, the snapshot that summarizes them survives, and the tail continues. The stream stays live and the cache is deliberately left untouched, because invalidating every cached entry on a housekeeping prune would be a self-inflicted thundering herd. That non-invalidation is a feature. It is also, it turns out, the exact condition under which the warm read's missing flag becomes corruption.

Picture a lagging cache entry. One process checkpointed stream X at count three and event id N; another process advanced X to seven, minting fresh snapshot boundaries above N, then ran a prune that deleted the domain events between N and the newest snapshot. Now the first process loads X. It has a warm entry at count three, so it queries `{ after: N }`. The events that used to sit between N and the snapshot are pruned away. The snapshot that would restore them is still there — but the query didn't ask for snapshots, so the store filters it out. What comes back is only the surviving tail, and the fold cheerfully applies that tail on top of the stale count-three state. The load returns four where the truth is seven.

The reason this is worse than a wrong number is what happens to `version`. The fold runs through the surviving tail event, whose version is the true head. So the returned snapshot carries state count-four and version-head at the same time. The next `app.do` computes its new events from count four and commits at `expectedVersion = head`, and the optimistic-concurrency guard — the one mechanism that exists to catch a stale read before it writes — sees the head version, waves it through, and never fires the `ConcurrencyError` that would have invalidated the cache and forced a correct reload. The self-correcting cache stopped self-correcting, silently, and the guard that should have noticed was blinded by a version number the fold made look current.

---

**The wrong turn: invalidate the cache on prune, or version-compare on write.**

The tempting fix is to make windowed close invalidate the cache entries for the streams it prunes. It closes the hole, and it throws away the reason windowed close exists. Prune is meant to be cheap background housekeeping on live streams; making it fan out cache invalidations couples a low-cadence maintenance operation to the read hot path and reintroduces exactly the herd the untouched-cache design avoided. The second temptation, teaching the cache write to compare versions and refuse stale checkpoints, is aimed at the wrong layer entirely — the stale entry here is not a racing write, it is a legitimately older checkpoint that the read path is supposed to be able to resume from. Both fixes treat the cache as the thing that broke. It isn't. The read query is.

The fix is one flag. The warm read asks for `{ after: cached.event_id, with_snaps: true }`. `after` still bounds the scan to events past the checkpoint; `with_snaps` keeps a snapshot in that window from being filtered out. They are independent store conditions and every adapter already honors both together — the snapshot resume floor stays inert because an explicit `after` overrides it, but the snapshot rows survive the filter. When a rebaselining snapshot falls in the after-window, the fold hits it, adopts its state wholesale, and continues from there; count seven, correct. When no snapshot falls in the window — the overwhelmingly common case — the flag changes nothing and zero extra rows are read. The optimization is untouched for every load that isn't downstream of a prune, and correct for the ones that are.

The rule worth keeping: a resume-from-checkpoint read has to request everything that could rebaseline it, not just the events it expects to replay. The warm path assumed the only thing after a checkpoint was more domain events. A prune can leave a snapshot as the only survivor above a stale checkpoint, and a read that filters snapshots out will fold right past the one row that would have told it the truth.
