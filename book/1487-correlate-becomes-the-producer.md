# What a watermark stopped meaning

The subscription work set arrived in two halves, and the first half was the easy one. A column landed on the subscription row, `correlated_at`, holding the highest event id known to resolve to that target, and `claim` learned to serve a marked stream from the row alone instead of probing the event log once per eligible subscription. It shipped dark, because nothing wrote a mark. Every row stayed null, null meant unknown rather than empty, and every claim took the legacy probe exactly as before. The measurements were there to prove the fast arm worked when a mark existed, and the fast arm was unreachable in a real app.

The second half is a producer. Only one component can be it. The store cannot resolve a target, because a resolver is arbitrary user code the store never sees. Resolving at commit time misses every event this process did not write, which is to say a remote writer, a direct store commit, a restore, a replay. The notify channel is documented as best effort, and a producer permitted to drop signals needs a pull backstop, which is the join the whole plan exists to delete. That leaves correlate, which already walks events forward, already applies each resolver, and already calls subscribe with what it found. It was throwing away the id at which it found the work and letting claim reconstruct it by brute force microseconds later.

So correlate records the id instead of discarding it, and two things that used to be true stopped being true. It walks static resolvers now, not just dynamic ones, because a static target is subscribed once at init and then never looked at again, and a target correlate never marks is a target claim never serves. And it no longer returns early for an app whose reactions are all static. Those apps used to skip the forward scan entirely. They pay for it now, and the ticket was gated on measuring how much rather than on assuming it was free. A Postgres app committing one event and settling it pays about two milliseconds more per round, which is two extra scans and one subscribe. Batching amortizes it, because the cost is per correlate window rather than per event, so the same app catching up on five thousand events pays fourteen percent rather than forty. That subscribe was seven round trips inside its transaction, three of them separate updates for priority, lane and the mark, which was fine when subscribe ran only on discovery and is not fine now that it runs on every scan. They are one statement now, and the no-op case still writes nothing.

The first wrong turn was thinking the in-process dedup could survive. Correlate keeps a bounded map of what each target was last subscribed at, so a resolution that resolves nothing new issues no store call. Marking every target on every scan is exactly the opposite of that, so the map lost its job of deciding whether a target is sent. Deleting it looked clean until the second reading, which is that subscribe writes the lane column unconditionally, by design, because re-laning is restart driven. A mark-carrying upsert that omits the lane resets a stream to the default lane, silently, on a path that now runs constantly. The map kept its memory and changed its job. A resolution that beats the target's recorded priority floor raises priority and lane; one that does not re-sends the values the row already holds, so the mark travels on an upsert that changes nothing else. Static targets sit at an infinite floor, which is how a dynamic resolution still cannot re-open what the build-time subscribe owns.

The second wrong turn was more interesting, and a recipe test found it rather than a unit test. A recurring reminder timer emits a terminal event when its loop ends, and an autoclose policy reaps the stream the moment that event is the head. It stopped reaping. The reason is a sentence that should be written on the wall of every system that replaces a pull with a push. Under the probe, a subscription was handed every event in its source window and acked past the ones that produced no work for it, so its watermark tracked what it had seen. Under the mark it is handed only what correlate marked for it, so its watermark tracks what it has consumed. A reaction on two of a state's ten event types now sits below that stream's head forever, with nothing pending, and the close cycle's safety probe, which refuses to truncate a stream while a consumer is behind, read that as a reader still in flight and skipped the close permanently.

Two repairs were available and one of them was a trap. The trap was to make correlate mark the last event in a target's source window whether it resolved there or not, which would restore the old watermark behavior everywhere and require no reader to change. It also reinstates the empty lease and no-op ack per subscription that an earlier ticket removed, contradicts the claim that the correlated set contains only streams with work, and is a heuristic rather than a rule, because it holds when the resolving and non-resolving events share a scan window and fails silently when they do not. The repair that survived was to fix the question. The probe wanted to know whether any consumer had unconsumed work below the head, and it was approximating that with whether any consumer's watermark was below the head. The mark answers the real question exactly, because it is the same predicate claim applies, so the probe reads it off the position and treats an unmarked row as pending, conservatively, the same way claim treats it as unknown. That cost one optional field on the position type, which is the kind of surface addition the RFC gate exists to make someone write down.

What is worth keeping from all of this is not the column or the index. It is that a watermark was carrying two meanings at once, seen and consumed, and nobody noticed because a pull-based claim kept them equal. Splitting them was the point of the change. Finding every reader that had quietly depended on them being the same number is the work the change actually cost.
