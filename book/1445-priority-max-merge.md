# The guard that repeated what the SQL already said

The SQLite adapter merged a re-subscribed stream's priority with one statement that was already complete on its own. Update the row to the new priority where the stored priority is less than it. That is the maximum rule, stated in SQL, correct for every number anyone could pass. Wrapped around it was an `if (priority > 0)`, which looks like a cheap optimization and reads like a sanity check, and is in fact the bug. Any re-subscribe at zero or below skipped the merge entirely, so a stored negative priority could never be raised again.

For a long time that cost nothing, because priorities in practice are positive. The place it surfaces is the one call that is allowed to move a priority downward. `prioritize` is documented as the operator's runtime override, the escape hatch for saying this stream should drain last for a while. Subscribe, by contrast, is restart-driven: every reaction target re-subscribes on every boot, at its declared priority. On the two other adapters those two facts compose into something sensible, where an operator can de-prioritize a noisy stream during an incident and the next deploy restores the declared value automatically. On SQLite the de-prioritization was permanent. The stream kept draining last, forever, and the only way back was another explicit `prioritize` call by someone who remembered doing the first one.

What makes this worth writing down is not the fix, which is deleting four characters and an indent level. It is why three adapters, a contract test suite that runs against all of them, and a doc-comment that states the rule in plain English all failed to notice for as long as they did. The contract test asserted that a re-subscribe at priority ten beats three, that a later one at one does not lower it, and that the omitted default does not lower it either. Every value in that sequence is positive, except the default, which is compared against a stored ten and so never exercises the merge at all. Against positive priorities the extra guard is a no-op, so the test passed on the adapter that had the bug just as cleanly as on the two that did not. The suite was testing the rule on the half of the number line where the rule happened to be implemented.

The repair to the test is more interesting than the repair to the code. Two cases now run against every adapter. The first walks the max rule through negative values, where a less negative priority must win and a more negative one must not, and finishes by checking that zero outranks a negative even when it arrives as the omitted default. The second states the operational property directly rather than the mechanical one: after a `prioritize` downgrade, the next subscribe restores the declared priority. That second test is the one that would have caught this from the operator's side rather than the implementer's, and it is the shape worth reaching for, because it fails for a reason someone can act on.

The generalizable habit is to distrust a guard that duplicates a condition already expressed downstream. `WHERE priority < ?` and `if (priority > 0)` are not the same predicate, and only one of them is the rule. When a check exists purely to skip work that would have been a no-op anyway, it has no upside to pay for the chance that it is subtly narrower than the thing it is guarding. It also invites the test author to write only the examples the guard permits. Both halves of that happened here.
